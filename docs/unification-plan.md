# 单设备程序 + 单 PC host：合并计划

状态：实机测试版已实现，2026-11-04。合并设备文件、新 PC host 和桌面模拟已完成；首轮刷入后报告菜单出现、LED 滚动 MemoryError；常驻内存优化未解决，进一步定位到整模块编译峰值。RAM2 分块版本已在真实设备 RAM 中通过启动、旋律加载和自动暂停退出，用户已确认手动重刷 RAM2 后正常；完整 PC 音画同步和连续切换仍待验收。使用入口见[合并版说明](../projects/unified/README.md)。

## 已确认的行为

用户确认采用以下切换规则：

- 上电立即进入独立模式菜单，无需等待电脑。
- “连接 PC”以匹配版本的 host 完成握手、曲库和音频准备为准。USB 供电、电脑开机或 Chrome 串口连接本身不触发 PC 模式。
- 独立模式在游戏、暂停或结果页中收到 host 就绪，只记录待切换状态；回到菜单才切换。
- PC 模式中 host 主动退出或心跳超时，结束当前未完成的 PC 局，清空 PC 谱面与计时状态，返回独立模式菜单。
- 不尝试接续断线前的歌曲或得分；重新连接后重新握手、加载、开局。
- 拔掉 USB 后继续运行需要 GamePad 电池或其他供电。若拔线导致设备断电，下次上电重新进入独立模式。
- 后续统一通过 Chrome 的 micro:bit Python Editor 手动导入并刷入生成的一个设备文件，不增加命令行刷写工具。

## 目标结构

合并开发放在 `projects/unified/`，原有两个项目在验收前保留。

已提供的测试版入口：

```text
projects/unified/
  src/microbit_main.py   # 可读主程序；共同引擎、两种后端、连接监督
  deploy/main.py        # 生成的唯一设备文件，Chrome 手动刷入
  pc_host.py            # 唯一 PC host；曲库、音频、连接管理
  tools/build.py        # 生成内嵌资源与单文件设备程序，不执行刷写
  tests/                # 离线回归、协议及连接模拟
```

上述入口已创建。设备程序共同使用原独立版 OLED 与游戏循环，保留各模式判定差异；连接状态机、分帧器在构建时内联，生成文件约 20 KB，以小启动器分块编译注释载荷，避免同时编译整模块。生成文件设 20,000 B 门槛，并执行标识符变换可逆检查；Base64 资源解码后的旋律、谱面和实际音高频率与基线完全一致。

设备端分工：

1. 共同引擎负责方向输入、计分、暂停时钟、OLED 和结果页面。
2. 本地数据源复用内嵌 MEGALOVANIA、ChartReader 和 Melody，音乐始终指定 P12，P0/P1 留给摇杆。
3. PC 数据源负责经过校验的谱面流，不播放设备旋律；host 独占 PC 音频。
4. 连接监督在所有页面持续运行，模式变化通过显式动作通知引擎停止声音、清空队列和重置时间。

切换到 PC 时先停止 P12 音乐；回独立模式时废弃旧串口片段、旧曲库加载事务、预定音频开始时间及 PC 计分状态。完成回退后才允许重新开局。

## RH1 协议草案

旧 host 的 CAT/META/N 等消息不能直接启用合并程序的 PC 模式。新增协议前缀和会话标识，后续设备与 host 同步升级。

- 115200 baud，ASCII，每帧换行结束，帧正文最多 60 bytes。
- 官方 UART 文档说明 RX 缓冲为 64 bytes，发送方初版采用一帧一确认，不能一次突发写入多个帧。分帧器有界不能替代发送端流控。
- 每次设备启动及连接失效后生成新的 8 位十六进制 device nonce；每次 host 连接生成新的 8 位 host nonce。会话标识为两者拼接的 16 位小写十六进制字符串。失效后轮换设备 challenge，避免旧 ATTACH 和 READY 重新启用过期会话。
- 心跳初值为 500 ms，连接租约为 2500 ms；均需实际设备压力测试后调整。
- 仅当前会话的及时心跳续约；过期会话不能由迟到心跳复活。新 host 不接管仍有效的旧 host 会话。
- 设备和 host 都检查对方存活。host 发现设备断线也必须停止音频和取消延迟启动，不能依赖设备发出 STOP。

握手顺序：

1. 设备周期性发 `RH1,HELLO,<device_nonce>`，host 启动后也能发现已经开机的设备。
2. host 发 `RH1,ATTACH,<device_nonce>,<host_nonce>`，设备核对版本与本次连接窗口的 challenge 后接受。只有通过该新鲜握手校验，才调用状态机的 `attach_host()`；测试版已实现 challenge 的生成、轮换与消息校验。
3. 双方确认完整 session。host 预检音频输出、有效歌曲和谱面；分帧发送曲库，设备事务性接收，完成前不替换菜单。
4. 只有曲库提交成功且 host 音频准备完成后，连接监督收到 ready 事件。
5. 设备在菜单内提交 PC 模式。host 在收到设备 SELECT/START/SYNCED 之前不加载开局时间或播放音频。

测试版实际消息：

- host 控制帧 `RH1,<session>,<seq>,<command>,...`；设备回 `RH1,<session>,A,<seq>,OK`。序号为 0..65535 循环，每次只允许一帧在途。
- host 控制包括 HB、EA（确认设备事件）、CATBEGIN/CAT/READY、BEGIN/N/END/ARM/SYNC、ERROR/BYE。每个已校验的新控制帧都可续约；空闲时每 500 ms 发 HB。重复帧只重新确认，不重复执行或续约。
- 设备事件 `RH1,<session>,E,<event_seq>,<command>,...` 包括 SELECT/START/SYNCED/NEED、PAUSE/RESUME/STOP/DONE/STARVED。设备同样逐事件等待 EA 并重发，host 按事件序号去重。
- 曲库最多 12 首，标题 ASCII；曲库完成前不可进入 PC 菜单。谱面携带 round ID、连续 note index、时间与方向；初始 24 条，后续最多 12 条，设备队列最多 48 条。
- 错会话和未完成握手的数据不生效；旧局已在途数据在取消后可以确认并丢弃。非法/过长行丢弃到换行；连接失效时清除未完成分帧和设备事件。

`protocol.py` 负责分帧，实际握手、命令语义和 ACK 在设备适配器与 `pc_host.py` 中实现。

## 计时和 host 改造重点

现有 host 在 `wav_for()` 中同步执行 FFmpeg，发送初始 24 个音符时还会累计约 528 ms 的显式 sleep；这些步骤不能阻塞新心跳循环。测试版在打开串口前完成全部可用歌曲的验证和 WAV 转换；随后由一个非阻塞主循环独占串口与 pygame 控制，无额外通信线程。事件确认优先于后续谱面批次，谱面逐条 ACK，不使用批次 sleep。

PC 模式的设备判定时钟必须由一次明确的 SYNC 启动事件确定。现有 host 在收到 SYNCED 后重新计 2700 ms，会叠加收包延迟；初版保留可调音频偏移，测量实际同步误差后再优化，不承诺零延迟。暂停和恢复使用同一局的冻结时间，通信心跳不随游戏暂停。

host 默认自动发现唯一匹配的 micro:bit USB 串口，并保留 `--port` 供多设备或手动选择。端口忙时给出明确错误，不抢占 Chrome 编辑器连接。host 在串口异常、设备心跳超时和正常退出的 `finally` 清理路径中都停止 pygame 音频并清除延迟播放任务。

连接有效但谱面补给超时，也不能让游戏继续吞掉缺失音符并计 Miss：测试版在队列无待判定音符且超过 4 秒未收到新谱面时取消本局，停止 PC 音频；连接仍健康时回 PC 选歌菜单，连接失效则回独立菜单。

### 3. 接入 PC 后端与新 host（软件完成，待实机）

### 4. 切换、压力与故障验收

| 场景 | 预期 |
| --- | --- |
| 仅电池/外电，或 USB 供电但没有 host | 独立模式立即可用 |
| host 已启动或之后启动 | 握手及准备完成后在菜单进入 PC 模式 |
| 独立局中启动 host | 当前独立局继续，返回菜单后切换 |
| PC 局中 host 正常退出、崩溃或 USB 断开 | 结束 PC 局，清空会话，回独立菜单；host 端也停止音频 |
| PC 暂停时断线 | 同样回退，不因暂停而停止心跳检查 |
| 迟到 NOTE、旧 READY、重复帧 | 不影响新局或独立模式 |
| 音频转换慢、串口分片/积压、谱面断供 | 心跳保持独立，数据错误按明确期限回退 |
| 时钟回绕和连续多次重连 | 不误续约、不保留旧计分或旧计时器 |

同时记录最坏循环耗时、UART 积压、板上可用 RAM、生成文件体积以及音画偏移。完成软件和硬件验收后，再决定是否移除旧项目入口。
